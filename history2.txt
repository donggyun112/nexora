pragmatist
💬 speak → @everyone
Vector DB vs Structured Memory comes down to three hard numbers: latency, cost per query, and who maintains it.

**Vector DB (Pinecone, Weaviate):**
- Indexing cost: ~$0.10-0.30 per 1M vectors/month (managed) or self-hosted at 8-16GB RAM per 1M vectors
- Query latency: 50-200ms at scale. Can hit 10s of milliseconds with local disk, but then you own the ops
- Failure mode: Semantic drift. You get answers that *sound* right but contradict your schema

**Structured Memory (KG/SQL):**
- Setup: 2-4 weeks of schema design, entity linking, maintenance pipelines
- Query latency: <10ms on indexed SQL, but requires exact queries or SPARQL—no fuzzy match
- Maintenance: Someone engineers entity resolution and keeps the KB consistent. ~$50-100K/year in labor

**The real trade-off:**
Vector DB wins if:
- Your agent handles open-domain queries where "approximately correct" is fine (customer support, Q&A)
- You don't need audit trails (you can't explain why the system retrieved that memory)
- You accept 5-10% hallucination from semantic similarity gaps

Structured Memory wins if:
- Your agent must cite sources or justify decisions (finance, legal, healthcare)
- You need sub-millisecond response or high throughput (>1000 queries/sec)
- Your domain is bounded and schemas don't shift weekly

**My call: Hybrid, but biased toward Vector DB for MVP.** Start with Vector DB for 3 months. If you hit semantic retrieval failures >2% or latency >300ms, then bolt on a KG layer for critical entity resolution. Don't engineer the KG upfront—you'll pay for schema you'll throw away.

Cost/benefit: Vector DB DIY on Postgres + pgvector = $500/month infra, zero maintenance headcount. KG = $100K+ annual engineering debt before it pays off.

systems_eng
💬 speak → @everyone
Systems perspective: We're debating theory without the operational constraints. Let me ground this in P99 latency, memory, and throughput—the metrics that kill agents in production.

**Vector DB (e.g., pgvector on Postgres):**
- Query latency: pragmatist said 50-200ms at scale. That's indexed nearest-neighbor. But agent loops are sequential: retrieve → LLM forward pass → action. If you're doing 1000 agent steps/hour, 150ms retrieval × 1000 = 2.5 minutes retrieval overhead per hour. Acceptable if LLM inference is 500ms+.
- Memory footprint: 1M embeddings (1536-dim, float32) = 6GB. Per 10M embeddings = 60GB. If your long-term memory is 100M tokens worth of context, you're looking at 12-15 embeddings per 100 tokens (rough), so ~1.5B embeddings = 9TB at single-copy. Replication for HA? Double that.
- Failure mode empiricist nailed: You can't audit why it retrieved X. Agent fails on task Y, you read the retrieval logs, see "cosine=0.87", and can't explain whether it was wrong embedding, wrong schema, or user input ambiguity.

**Structured Memory (KG + SQL):**
- Query latency: <10ms on indexed SQL is accurate IF your schema is designed. But design is 80% of the cost. For "retrieve all purchases by user X in Q1 2026 where category contains 'electronics'", that's 2 SQL joins, microseconds. For "find similar users to X," you're back to KG traversal, which is Dijkstra's algorithm, non-trivial at million-node scale.
- Memory footprint: A 1M-entity KG (entity type, properties, relations) in RDF/Neo4j is roughly 50-100GB depending on edge density. Much smaller than vector embeddings for the same semantic coverage.
- Latency variability: Worst case is query planning. A pathological join can spike to seconds. With vector DB, latency is more predictable (LSH/HNSW is O(log n)).

**The real trade-off no one's quantified yet:**
- Agent inference: 1 step = (LLM forward 200-500ms) + (memory retrieval 10-200ms) + (action 50-500ms).
- Vector DB: Retrieval is fast, but you might need 5-10 retrievals to correct for semantic drift (requery, different prompt, rerank). Total: 50-2000ms extra per agent step.
- Structured Memory: First retrieval is exact, but agent needs a translator (natural language → SQL/SPARQL query). Current LLM→SQL accuracy is ~70-80% on complex queries. Miss rate 20-30% means fallback to vector DB or human intervention. Total: 10ms retrieval + 200-500ms LLM "query planning" + potential retry.

**What we need to decide:**
1. **Agent task criticality:** Legal/finance contracts? Structured Memory non-negotiable. Customer support FAQ? Vector DB fine.
2. **Query diversity:** Open-domain chatbot? Vector DB. Transactional agent (book flights, manage inventory)? Structured Memory.
3. **Budget reality:** $500/month pgvector + hidden 2-3 FTE for retrieval debugging? Or $5-10K/month managed KG + 1 FTE for schema management?

**My recommendation to moderator:**
Profile your agent's actual memory access patterns first. Log 100 agent runs. Measure:
- % of memory queries that have a clear entity/relation structure (e.g., "get user X's order history") vs fuzzy semantic queries (e.g., "find similar products")
- Current latency budget: Can you afford 200ms retrieval per agent step?
- Audit cost: If a mistake happens, how much human investigation time is acceptable?

If >70% of queries are structured, go KG. If <30%, Vector DB MVP. If 30-70%, **hybrid: Vector DB for retrieval, KG as validation layer** (LLM-generated SQL gets executed and results cross-checked with vector retrieval).

Numbers, not theory. What's your actual agent loop looking like?
